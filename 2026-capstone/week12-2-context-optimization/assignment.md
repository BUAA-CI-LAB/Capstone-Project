# 第十二周作业：计算与缓存方向的优化对比

## 任务

本周以小组为单位完成，**每组提交一份**。在 DGX Spark 上分别从计算和缓存两个方向对比优化前后的效果，**两个方向都要完成**。实验均在 PyTorch 与 Transformers 中进行，不需要改动本组的 vLLM 服务。核心代码可以参考课件 6.2 页，测试脚本由各组自行编写。

| 方向 | 对比内容 | 对应课程内容 |
| --- | --- | --- |
| 计算 | 标准 Attention（eager）与 FlashAttention | 第 1 次课 1.1、2.1–2.6 |
| 缓存 | 集成 StreamingLLM、SnapKV 或 LLMLingua-2 中的一项，与不压缩对比 | 第 2 次课 3.2–3.4 |

### 方向一：标准 Attention 与 FlashAttention

用同一组随机生成的 Q、K、V，分别用两种实现计算 Attention 前向。

- **标准实现**：逐步调用 PyTorch 算子，依次计算 `QKᵀ / √d`、因果掩码、按行 softmax 和乘 V，中间生成完整的 N×N 矩阵。softmax 可以先转为 FP32 计算。
- **FlashAttention**：调用 `F.scaled_dot_product_attention(q, k, v, is_causal=True)`，并用 `sdpa_kernel(SDPBackend.FLASH_ATTENTION)` 指定实现。DGX Spark 上如果报 `No available kernel`，改用 `CUDNN_ATTENTION` 或 `EFFICIENT_ATTENTION`，并在报告中写明实际使用的后端。

统一设置为 BF16、batch 1、8 个头、head 维度 128、因果掩码，序列长度 N 取 1K、2K、4K、8K。标准实现最多测到 8K，FlashAttention 可以继续测到 16K 或 32K。

每个长度记录以下指标。

| 指标 | 测量方法 |
| --- | --- |
| 前向时延 | 预热后重复 10 次，取中位数；计时前后调用 `torch.cuda.synchronize()` |
| 额外显存 | 测量前调用 `torch.cuda.reset_peak_memory_stats()`，用调用后的 `torch.cuda.max_memory_allocated()` 减去调用前的占用 |
| 最大误差 | 与 FP32 标准实现结果相比的最大绝对误差，在 N ≤ 4K 时计算 |

### 方向二：集成一项长上下文压缩技术

从第 2 次课讲过的三项技术中任选一项，集成到 Transformers 推理流程中，与不压缩的结果对比。

| 技术 | 类型 | 参考实现 |
| --- | --- | --- |
| StreamingLLM | KV 压缩，保留开头少量 token 与最近的窗口 | kvpress 的 `StreamingLLMPress` |
| SnapKV | KV 压缩，按末尾观察窗口的注意力选出重要位置 | kvpress 的 `SnapKVPress` |
| LLMLingua-2 | 提示词压缩，按 token 分类结果删减输入文本 | llmlingua 包的 `PromptCompressor` |

也可以不使用这两个库，按论文自行实现，在报告中说明实现方式。kvpress 与 llmlingua 对 Transformers 的版本有要求，**建议安装在单独的虚拟环境中，不要改动 vLLM 的环境**。使用 kvpress 前先确认所用模型在其支持范围内。LLMLingua-2 的模型需要提前准备，校园网无法直连 Hugging Face 时，可以在本机下载后上传。

评测使用长文档问答，也就是课上提到的“大海捞针”。

- 模型使用共享目录 `/srv/spark/models` 中的 Qwen3-1.7B，解码使用贪心（`do_sample=False`）。
- 在 4K 和 8K token 的长文本中插入一句包含答案的话，分别放在约 10%、50%、90% 的位置，再提出问题。每个“长度 × 位置”组合至少 5 个问题，答案用代码判定，例如检查回答中是否包含正确的数字或关键词。
- 删去比例取 0.25、0.5、0.75，与不压缩的结果对比。KV 压缩的删去比例对应 kvpress 的 `compression_ratio`；LLMLingua-2 的 `rate` 表示保留比例，对应取 0.75、0.5、0.25。
- 记录答对率与端到端时延。KV 压缩另外报告 KV 显存，可以用峰值显存，也可以按保留的 token 数估算；提示词压缩另外报告压缩前后的输入 token 数和压缩本身的耗时。

使用 kvpress 时，pipeline 中单独传入的 `question` 不参与压缩。选择 SnapKV 的小组可以再试一次把问题放在 context 末尾，比较两种做法的结果。

### 需要回答的问题

计算方向：

1. 标准实现的额外显存随 N 怎样增长？与 N×N 矩阵的理论大小是否一致？例如 8 个头、N = 8192 时，一份 BF16 的分数矩阵约为 1 GiB。
2. FlashAttention 的加速比随 N 怎样变化？原因是什么？
3. 两种实现的输出差多少？差异来自哪里？

缓存方向：

1. 压缩省下了多少显存或输入 token，时延有何变化？
2. 答对率随删去比例和答案位置怎样变化？答案在中间时是否更容易丢失？
3. 所选技术为什么会保留或丢掉答案所在的内容？

### 统一要求

- 同一方向的各组设置只改变被比较的一项，输入、模型与解码参数保持一致。
- 每组设置先预热再测量，时延取多次测量的中位数。
- DGX Spark 由多个小组共用，实验期间注意内存占用，结束后及时退出进程。
- 某一步未跑通时，提交已有结果、报错原文与排查记录。本周作业的重点是用同一套设置测出优化前后的差别，并用数据解释原因，不以是否得到预期的加速或答对率作为标准。
