# 第七周作业：Agent 框架服务测试与 Metrics 收集

## 任务概述

将本组已有的 Agent 框架接到 DGX Spark 上运行的 vLLM 服务，先验证功能正确性，再在固定任务下测量服务指标。重点不是追求某个绝对速度，而是建立一套能复现、能比较的测试方法：同一 Agent、同一任务集、同一测量口径下，记录配置变化带来的实际影响。

使用本组账号登录 DGX Spark，并使用本组约定端口。不要使用其他小组的账号、目录和进程，不要提交账号密码、访问令牌或他人的原始数据。

## 第一步：跑通 Agent 框架

1. 按本讲 README 启动 vLLM 服务，记录模型、vLLM 版本、完整启动命令和服务端口。
2. 将 Agent 框架的模型接口改为该服务的 OpenAI 兼容地址，例如 `http://127.0.0.1:${PORT}/v1`，模型名与 `--served-model-name` 保持一致。
3. 选一组能代表本组 Agent 实际用途的固定任务，建议 10–20 个，覆盖正常完成、需要工具调用和容易失败的情形。任务集确定后，整个作业不要更换。
4. 先小规模运行，确认 Agent 能完成任务、工具调用链完整、输出能被框架正确解析，再开始计时。功能跑不通时先修框架，不要用性能数据代替功能验证。

每个任务至少记录：

| 字段 | 说明 |
| --- | --- |
| 任务编号与输入 | 能定位到原始任务，敏感内容可脱敏 |
| 完成状态 | 成功、失败、超时或解析错误 |
| 总耗时 | 从提交任务到 Agent 给出最终结果 |
| 模型调用次数 | 一个任务触发了多少次模型请求 |
| 输入 / 输出 token | 框架或接口能提供时填写，不能提供时注明 |
| 结果摘要 | 最终输出或失败原因，不要只写“完成” |

## 第二步：用 bench_lab.py 建立服务基线

在 Agent 正式测试之外，用本讲的 `bench_lab.py` 对同一服务做一组受控测量，作为后续比较的基线。

至少完成：

1. **并发扫描**：并发 1、4、8、16，输入 512、输出 128 token。
2. **一组单变量对比**：从 Prefix Caching 开关、每轮 token 预算、KV 容量、默认模式与 `--enforce-eager` 中任选一项，只改变这一个变量，其余条件保持不变。
3. 每种配置先预热；正式测量时请求数应足以计算尾部分位数，并在报告中写明请求总数与失败数。

示例命令：

```bash
python bench_lab.py \
  --base-url "http://127.0.0.1:${PORT}/v1" \
  --model qwen3-1.7b \
  --concurrency 4 \
  --num-prompts 32 \
  --max-tokens 128 \
  --label baseline-c4 \
  --output outputs/baseline-c4.json
```

不要把 `bench_lab.py` 的短请求结果直接当作 Agent 任务耗时。短请求用于隔离服务本身的表现，Agent 实测用于观察完整框架的端到端表现，两者要分开报告。

## 第三步：收集服务 Metrics

Agent 测试和受控测量期间，同时记录服务端指标。vLLM 在同一端口提供 `/metrics` 接口，可在测试开始前、测试中和结束后各保存一份快照：

```bash
curl -s "http://127.0.0.1:${PORT}/metrics" -o outputs/metrics-before.txt
# 运行测试……
curl -s "http://127.0.0.1:${PORT}/metrics" -o outputs/metrics-after.txt
```

重点关注并在报告中说明口径：

- 请求侧：完成、失败或取消的请求数，队列中等待与正在运行的请求数；
- 延迟侧：TTFT、TPOT、ITL 的累计分布或分位数；
- 吞吐侧：输入 token 与生成 token 的累计量及测量窗口内的速率；
- 资源侧：KV Cache 使用情况与 Prefix Cache 命中情况。

不同 vLLM 版本的指标名可能略有差异，以本机 `/metrics` 实际输出为准。快照包含累计计数时，要用结束值减去开始值再除以测量时长，不要把累计值直接当成速率。

## 第四步：做一次有依据的调整并复测

根据前两步结果选一个问题做调整，例如入口并发、Prefix Caching、每轮 token 预算、KV 容量或编译模式。要求：

1. 先写清观察到的问题和准备验证的判断。
2. 一次只改一个变量，Agent、任务集、并发和测量命令保持不变。
3. 用完全相同的口径复测，并把调整前后放在同一张表中比较。
4. 如果差异接近波动，如实说明，并增加样本复测；不要只挑最好的一次结果。

## 提交内容

提交一个小组目录，至少包含：

```text
submission/
├── report.md              # 本次测试报告
├── agent/                 # 本组 Agent 框架代码或相对原框架的改动说明
├── configs/               # 服务启动命令、Agent 配置（删除密码和令牌）
├── outputs/               # bench_lab.py 的 JSON、metrics 快照和任务结果汇总
└── figures/               # 报告中用到的图表（可选）
```

`report.md` 至少包含：

1. **环境与配置**：模型、vLLM 版本、服务启动命令、Agent 框架版本、任务集来源和规模；
2. **功能测试结果**：任务成功/失败统计、典型成功与失败各一例及原因；
3. **服务基线**：并发扫描与单变量对比的表格，注明请求数、输入/输出长度和测量工具；
4. **Agent 端到端结果**：任务总耗时、调用次数和 token 用量等汇总；
5. **Metrics 说明**：采集时间点、指标含义，以及由快照计算速率的方法；
6. **调整与复测**：改了什么、为什么改、调整前后对比和结论；
7. **复现方法**：从启动服务到运行 Agent、再到生成指标文件的完整命令。

## 验收要点

- Agent 能通过本地 vLLM 服务真实完成固定任务，而不是只展示单条聊天请求；
- 受控测量与 Agent 实测口径分开，配置、负载和样本量写清楚；
- Metrics 有采集方法、有时间窗口，不只给截图或单个瞬时值；
- 单变量对比确实只改变一个变量，结论能由提交的数据复核；
- 报告不包含账号密码、访问令牌和未经脱敏的他人数据；
- 实验结束后关闭本组服务，不遗留占用 GPU/内存的进程。
