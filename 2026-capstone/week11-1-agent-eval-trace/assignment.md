# 第十一周作业：完成 Agent v2，加入 Planning、评估与 Trace

## 任务

本周以小组为单位完成，**每组提交一份**。继续完善 Agent v1，在已有 Memory、Tool 和知识库的基础上加入 Planning，并在统一任务集上生成评估结果与完整 trace。

可以继续自己的项目，也可以参考[配套示例与运行说明](code/README.md)。应用场景、模型、框架和计划表示方式可自行选择。LangGraph 是课堂中的实现例子。

### 1. 完成 Agent v2

让计划实际参与任务执行，至少能够展示以下过程。

- 收到任务后生成显式计划，说明子任务、执行依赖与可观察的完成条件。
- 执行器读取计划，调用工具，并根据真实 Observation 更新进度。
- 出现信息缺失或工具失败时，能够修订剩余计划、有限重试，或说明原因后结束。为模型调用、工具调用和总耗时设置有限预算，在 trace 中记录结束原因。
- 保留原有 Memory、工具与知识库功能，说明 Planning 增加在哪些位置、解决了什么问题。

计划可以使用 JSON、列表或框架状态表示。报告中给出一条实际生成的计划，并指向相应的执行记录。只在最终回答中列出操作步骤，无法展示执行器使用计划的过程。

### 2. 固定统一任务集与成功标准

准备一份**至少 8 条任务**的任务集。两种版本和所有重复运行都使用这同一份任务文件、输入资料、初始 Memory 与评分规则。测试前保存任务集版本或文件哈希，调整任务或评分规则后重新评估两种版本。

任务应覆盖本组项目中有意义的能力，建议包含以下类型。

| 类型 | 可以检验的行为 |
| --- | --- |
| 常规任务 | 已有 Agent 能处理的基本问题，用于观察回归 |
| 多步任务 | 需要组合读取、检索、计算或写入等操作，能够体现 Planning 的作用 |
| 信息不足或边界任务 | 识别缺失资料、文件不存在或约束无法满足，并给出明确说明 |
| 工具异常任务 | 工具临时失败后重试、调整计划或正确终止 |
| 有状态变化的任务 | 本组有文件、数据库或其他写入能力时，检查实际产物或最终状态 |

每条任务至少写明 `task_id`、输入、类别和明确的成功标准，并提供参考答案、参考产物或人工核对记录，确认任务在给定环境中能够完成。信息不足的任务可以把“正确指出缺失”作为成功标准。

配套 [tasks.jsonl](code/tasks.jsonl) 提供 8 条课程示例任务，包括单次检索、多步问答、资料不足、文件缺失、一次检索超时与保存说明。继续自选项目的小组可以替换成适合本组场景的固定任务集，并说明各类任务检验的能力。

### 3. 在 DGX Spark 上运行评估

准备两个可比较的版本。

- **基线版本**使用加入 Planning 前的执行方式。可以保留一个关闭 Planning 的运行开关。
- **Agent v2**启用 Planning。

两个版本各在完整任务集上运行 **2 遍**，每次任务从相同的初始状态开始。按最低 8 条任务计算，共生成 `8 × 2 个版本 × 2 遍 = 32` 条任务执行记录。固定模型、服务参数、解码设置、工具、知识库、初始 Memory 和执行预算，并记录两版本的代码或提示词差异。若其他改动也影响结果，在报告中写明。

每条任务独立使用工作目录、会话和 Memory 初始副本。故障注入也应在每次试验中重新设置，避免后一次运行读到前一次生成的答案或产物。Memory 的跨轮效果需要通过任务内部的对话流程检验。

存在客观答案时优先使用代码评分。开放式内容可以使用明确的人工评分表或 LLM 裁判，写明评分依据。使用 LLM 裁判时，抽查判断理由并与人工核对。结束状态、任务得分分别记录，模型正常结束后仍需检查答案和实际产物。

至少汇总以下指标，注明分母、单位和统计方式。

| 指标 | 建议口径 |
| --- | --- |
| 任务成功率 | 通过成功标准的试验数 ÷ 已完成评分的试验数，同时列出评分失败数与评估覆盖数 |
| 各类任务成功率 | 按任务类别分别统计，定位哪一类能力变化 |
| 执行状态 | 完成、错误、超时、预算耗尽等状态的次数 |
| 效率 | 每任务耗时、模型调用数、工具调用数，以及接口提供的 Token 用量 |
| 工具执行情况 | 参数有效且执行无错误的调用数 ÷ 全部工具调用数，记录重试与恢复情况 |

本组采用结构化输出时，再统计格式合法率。工具异常任务中，首次故障会降低工具执行成功率，恢复后的任务仍可能成功，需要结合 trace 解释。

重复运行用于观察波动。保留两遍原始结果，可以按遍次列出成功数。使用温度 0 仍可能产生差异，两次试验的结果需要结合样本数解释。

### 4. 分析结果与 Trace

比较两种版本的任务成功率和执行开销，分析 Planning 在哪些任务上有帮助、哪些任务没有改善或出现退化。

选择**至少 3 条有代表性的完整 trace**进行分析，尽量包含一条多步任务、一条失败或恢复任务，以及一条能说明两版本差异的任务。若全部成功，可以分析恢复过程、额外调用或重复运行差异。

每条分析写明 `task_id`、版本、重复编号和 trace 文件位置，沿着“输入与初始状态 → 初始计划 → 工具调用与 Observation → 计划更新 → 最终回答或状态 → 评分依据”解释结果。指出错误首先出现在哪一步、属于哪类问题，以及结论对应的证据。

人工复核至少 2 条逐任务评分，优先检查被判失败或难以判断的案例。发现评分规则误判时，保留原始 trace，修正评分器并重新评分全部可比记录，说明修改原因。运行过程与评分过程分别记录错误，服务未就绪、数据错误或评分器报错也应留下排查记录。

### 5. 可选拓展

可以选择一项小体量拓展，例如修复一次明确的失败后重跑完整任务集、增加持久化检查点与恢复测试、加入多轮 Memory 评估，或接入 LangSmith 等可观测平台。记录改动、运行条件与真实结果即可。

配套示例提供本地 JSON trace。采用其他平台时，提交能查看的执行记录或导出文件。

## 运行参考

使用课程示例时，先按[运行说明](code/README.md)上传第六周资料、准备环境并启动模型服务，再在 Spark 上运行。

```bash
cd ~/week11/code
source ~/venvs/vllm/bin/activate
export PORT=8101  # 换成本组端口

# 验证评分器、状态隔离、故障恢复和预算控制
python eval_agent.py --selftest

# 两种模式、统一 8 条任务、每条各运行两遍
python eval_agent.py --mode both --repeats 2 \
  --base-url "http://127.0.0.1:${PORT}/v1" \
  --model qwen3-8b-bf16 --output results/agent-v2
```

`--selftest` 使用确定性测试输入检查程序逻辑。上面的第二条 Python 命令会调用 Spark 上的真实模型，输出 `manifest.json`、`summary.json`、`results.jsonl`、逐任务 `traces/` 和隔离的 `workspaces/`。再次运行时更换输出目录名，以保留已有记录。

自行实现的项目可以使用自己的命令与结果格式，在运行说明中写清批量评估入口和文件对应关系即可。
